**How each requirement is covered**

| Requirement | Implementation |
|---|---|
| Add, update and remove products | `POST`, `PATCH` and `DELETE` on `/api/products` |
| Product details (name, price, code) | `GET /api/products/:id`, which also returns the category name |
| Categories | Full create/read/update/delete on `/api/categories`. A category that still has products can't be deleted (409). |
| Sorting and filtering | `GET /api/products` filters by `search`, `categoryId`, price range, quantity range and `inStock`. It sorts by 7 fields and supports paging. |
| Increase or decrease stock | `POST /api/products/:id/stock/increase` and `/decrease` with `{ quantity, reason? }` |
| Stock never below zero | The service rejects it with a 422 and a clear message. The database also has a rule (`CHECK quantity >= 0`) as a second guard. |
| Total stock per category | `GET /api/categories/stock-summary` returns the product count, total quantity and total value per category, plus overall totals. |
| History of all changes | The `stock_movements` table records the change, quantity before and after, and the reason. It's available at `/api/stock-movements` and `/api/products/:id/stock-movements`. |
| Local relational database | SQLite through `better-sqlite3`. The file is `data/inventory.db` and is ignored by git. |

**Design decisions you might want to change:**
- **Quantity can't be edited with `PATCH`.** Stock only changes through the increase/decrease endpoints, so every change ends up in the history. Each change and its history record are saved together, so you can't get one without the other.
- **Deleting a product keeps its history.** The deletion is recorded as a `REMOVED` entry, and history entries store the product's name and code at the time.
- **Prices are stored as whole cents** to avoid rounding errors, and the API sends and receives normal decimals like `2.49`.
- **Product codes and category names must be unique**, ignoring upper/lower case (`bev-001` clashes with `BEV-001`).
- **New libraries:** `better-sqlite3` for the database and `zod` for input validation. I tried Node's built-in SQLite first, but it still prints an "experimental" warning.

## 2. Global error catching and logging

- **Logger:** [logger.js](backend/src/utils/logger.js) uses `pino`, replacing `morgan`. It writes JSON in production, readable coloured output in development, and nothing in tests. You can set the level with `LOG_LEVEL`.
- **Request logging:** [requestLogger.js](backend/src/middlewares/requestLogger.js) writes one line per request: info for success, warn for 4xx, error for 5xx. Every request gets an ID, sent back in the `X-Request-Id` header (reused if the client sends one) and included in error responses.
- **Error handler:** [errorHandler.js](backend/src/middlewares/errorHandler.js) catches every error from routes.
  - Known errors (validation, malformed JSON, oversized body, database rule violations) return the matching 4xx and are logged as warnings.
  - Anything else returns a generic 500, so no internal details reach the client, and is logged as an error with the full stack trace.
- **Crashes:** [server.js](backend/src/server.js) logs uncaught exceptions, unhandled promise rejections and startup failures as `fatal`, then shuts down cleanly and exits with code 1, so a process manager can restart the server.

I checked this on a live server. Production writes JSON log lines with matching request IDs. A broken database path at startup is logged as `fatal` and the process exits with code 1.
